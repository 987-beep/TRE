1. Upstream llama.cpp Revision Baseline:

   - In llama.cpp, KV cache management is implemented in `src/llama-kv-cache.cpp`.

     * Upstream llama.cpp historically allocated uniform KV cache buffers based on the
       maximum key/value head dimension across all layers.

2. FIVE APPLICATION RUNTIME ARCHITECTURES & COMPATIBILITY LIMITATIONS
================================================================================

1. NATIVE LINUX APPLICATIONS:
   - Primary Mechanism: Bubblewrap (`bwrap`) unprivileged user namespaces combined
     with Landlock LSM rules and Seccomp-BPF system call filtering.
   - Filesystem: Read-only mounts for `/usr`, `/lib`, `/bin`. Ephemeral `tmpfs` on `/tmp`.
     Isolated per-app data directory in `~/.var/app/<app-id>/`.
   - Network: Gated via `--unshare-net` unless explicitly requested in manifest.

2. BROWSER & PWA APPLICATIONS:
   - Primary Mechanism: KAATYA Browser (Chromium core) with multi-process site isolation,
     seccomp-bpf filters, and isolated user data directories per PWA context (`--app="URL"`).

3. ANDROID APPLICATIONS (WAYDROID / LXC):
   - Primary Mechanism: Linux Containers (LXC) running Android Open Source Project (AOSP).
   - Shared-Kernel Security Implications: Waydroid shares the host Linux kernel. Any kernel
     vulnerabilities (e.g. privilege escalation) can cross container boundaries.
     SELinux / AppArmor profiles are enforced to restrict container syscalls.
   - Filesystem & IPC: Android root (`system.img`) is isolated; host `/home` is hidden
     except for an explicit shared folder (`~/AndroidStorage/`). Binder IPC is isolated.
   - Store Ecosystem Realism: Google Play Store and Google Mobile Services (GMS) are
     proprietary and CANNOT be officially bundled without Google CTS/GTS hardware certification.
     Supported distribution: F-Droid (FOSS) and Aurora Store (with disclaimer).

4. WINDOWS APPLICATIONS VIA WINE / BOTTLES (LIGHTWEIGHT RUNTIME):
   - Primary Mechanism: Per-application Wine prefix managed via Bottles, executed inside
     an outer Bubblewrap sandbox container.
   - Wine Security Reality: A standard Wine prefix is NOT a security boundary; `wineserver`
     translates Win32 calls into unconfined host syscalls, and default Wine exposes the
     host root filesystem at `Z:\`.
   - KAATYA Hardening: The `Z:\` drive mapping is stripped. Wine runs inside Bubblewrap
     with `--unshare-all`, private `tmpfs`, and only the prefix directory writable.
   - Limitations: Anti-cheat systems, kernel-mode drivers, and proprietary Windows subsystems
     are unsupported.

5. WINDOWS APPLICATIONS VIA HARDWARE VM (FULL ISOLATION):
   - Primary Mechanism: QEMU / KVM virtual machine utilizing Intel VT-x hardware virtualization.
   - Windows 10 22H2 Lifecycle Warning: Windows 10 22H2 reached official End of Support (EOS)
     on October 14, 2025. After EOS, unpatched images are vulnerable to unpatched exploits.
     KAATYA isolates Windows 10 VMs behind an internal host-only bridge with no direct LAN routing.

6. MICROSOFT STORE & MSIX COMPATIBILITY RESEARCH:
   - Microsoft Store Limitation: The official Microsoft Store requires the proprietary Windows
     App Installer framework, Microsoft Account authentication, and UWP/WinRT APIs not implemented
     in Wine. Universal Microsoft Store integration is NOT possible on Linux.
   - MSIX Packages: MSIX packages are signed AppX zip containers. Unpackaged Win32 binaries inside
     MSIX can sometimes be extracted via `msix-unpack` and launched in Wine, but UWP apps fail.
   - Legitimate Alternatives: Direct Win32 installers (`.exe`/`.msi`), Bottles runner recipes,
     and Flatpak / F-Droid alternatives.

4. PROVISIONAL STORAGE, FILESYSTEM & RECOVERY ARCHITECTURE
================================================================================
The choice between Btrfs and Ext4 remains PROVISIONAL pending physical storage
benchmarks on the HP Slimline PC 270-p0xx hardware baseline in Stage 3.

1. PROVISIONAL DEFAULT TIER: BTRFS STORAGE WITH SUBVOLUME ROLLBACK
   - Subvolume Boundaries:
     * `@`            -> Root filesystem image (Mounted at `/`)
     * `@home`        -> User profile and personal files (Mounted at `/home`)
     * `@var_log`     -> System logs (Mounted at `/var/log`)
     * `@snapshots`   -> Storage location for read-only snapshots (Mounted at `/.snapshots`)
   - Crucial Subvolume Isolation: Btrfs snapshots are subvolume-specific. A snapshot of `@`
     strictly captures the root system tree; it does NOT include `@home` or `@var_log` because
     subvolumes act as independent filesystem trees. User documents and logs are preserved.
   - Writable Rollback Candidate Flow:
     1. Read-only snapshot created: `btrfs subvolume snapshot -r / /.snapshots/@_snapshot_ID`.
     2. To rollback, create a writable clone of the snapshot:
        `btrfs subvolume snapshot /.snapshots/@_snapshot_ID /@_rollback_candidate`.
     3. Update default subvolume pointer: `btrfs subvolume set-default <subvol_id> /`.
     4. Update GRUB menu: `grub-btrfs` script auto-populates boot options.
   - Failure Recovery:
     * Failed Kernel/Update: Select previous snapshot from GRUB boot submenu.
     * Failed GRUB Bootloader: Boot via live USB, chroot into system, reinstall GRUB (`grub-install`).
   - Honest Backup Disclaimer: Btrfs snapshots are NOT backups. They reside on the same
     physical disk blocks. Physical drive failure destroys both active data and snapshots.
     True backups require offsite or secondary disk copies.

2. FALLBACK TIER: EXT4 STORAGE WITH TIMESHIFT (RSYNC MODE)
   - Fallback Installation File System: Ext4 (Used if user overrides Btrfs).
   - Snapshot Mechanism: Timeshift in `rsync` mode using hard-links on Ext4.
   - Recovery Limitation: Ext4 snapshots cannot be booted directly from the GRUB menu.
     Rollback requires booting into a KAATYA Live USB and executing Timeshift restore.

2. CREDENTIAL VAULT ARCHITECTURE & MEMORY PROTECTION
================================================================================
- Master Key Derivation: User master passphrase + 32-byte cryptographically secure salt
  generated via `getrandom()` system call.
- `/etc/machine-id` Rejection: Explicitly rejected as secret or sole key source (world-readable).
- KDF: Argon2id (RFC 9106) with $m = 65,536\text{ KiB}$ (64 MiB), $t = 3$ iterations, $p = 4$ threads.
- Symmetric Cipher: AES-256-GCM with unique 96-bit random nonces generated per encryption.
- Kernel Session Keyring: Keys held ephemerally in Linux kernel keyring (`keyctl`).
- In-Process Protections: `mlock()` prevents swap paging; `madvise(MADV_DONTDUMP)` prevents core dumps;
  `explicit_bzero()` wipes buffers immediately after use.
- Security Realism: Root users (`CAP_SYS_PTRACE`), kernel modules, and cold-boot hardware attacks
  can extract keys from unlocked memory. Exposure window is minimized to microseconds.
- Logging: Structural JSON omission is the primary security boundary; regex filtering is secondary defense.

3. AI EMERGENCY STOP & LLAMA.CPP ABORT CALLBACK ARCHITECTURE
================================================================================

A. CORRECTION OF CANCELLATION API (`LLAMA_SET_ABORT_CALLBACK`)
--------------------------------------------------------------------------------
In upstream llama.cpp (see `llama.h`), the abort mechanism is `llama_set_abort_callback()`:

```c
typedef bool (*ggml_abort_callback)(void * data);
void llama_set_abort_callback(struct llama_context * ctx, ggml_abort_callback abort_callback, void * abort_callback_data);
```

Operational Implementation in `kaatya-aid`:
1. Registration: Upon initializing the `llama_context`, `kaatya-aid` registers an abort callback
   referencing a thread-safe atomic cancellation flag (`std::atomic<bool> g_abort_requested`).
2. Execution Check: During active `llama_decode()`, the CPU compute backend periodically executes
   the callback between token evaluations. If `g_abort_requested` is true, the callback returns
   `true`, immediately halting token generation and returning execution to the daemon loop.
3. Queue Eviction: All queued pending prompts are evicted immediately with `AbortError`.
4. Realistic Buffer Clearing: Plaintext prompt strings and response tokens in RAM are wiped
   using `explicit_bzero()`. Note: KV cache memory blocks are marked free; dirty cache pages
   are released or overwritten during subsequent inference.

B. CLOUD HTTP REQUEST CANCELLATION & REMOTE REALISM
--------------------------------------------------------------------------------
1. Local Sockets: The daemon triggers `SO_LINGER(0)` socket abort and terminates the HTTP/2 stream.
2. In-Flight Data Realism: A local TCP reset terminates client-side data receipt. However:
   * It DOES NOT retract data already transmitted across the Internet.
   * It DOES NOT guarantee the remote cloud provider has stopped processing the request.
   * In-flight token billing may still be charged by remote commercial providers.
3. Helper Processes: Helper sandboxes receive `SIGTERM`, followed by `SIGKILL` after 250ms.
4. UI Status: Displays prominent amber banner: "Inference Aborted by User".

================================================================================
4. USERSPACE MEMORY PRESSURE GOVERNOR (`KAATYA-MEMORYD`)
================================================================================
Linux Pressure Stall Information (PSI) is an accounting metric (`/proc/pressure/memory`),
not an automatic management daemon. KAATYA OS 3.0 deploys a dedicated userspace daemon:
`kaatya-memoryd`.

1. PSI MONITORING ENGINE:
   - Polls `/proc/pressure/memory` using `epoll` triggers on configured thresholds.
   - Threshold Tiers:
     * Level 1 (Elevated): `some avg10 > 15.0` (Memory bandwidth contention beginning).
     * Level 2 (High): `some avg10 > 30.0` or physical free RAM < 15% (2,457 MiB).
     * Level 3 (Critical): `some avg10 > 50.0` or physical free RAM < 8% (1,310 MiB).

2. TIERED MEMORY SHEDDING ACTIONS:
   - Level 1 Action: Signals Chromium via DevTools memory API to discard background tabs.
   - Level 2 Action: Freezes inactive Waydroid containers via cgroups v2 freezer subsystem;
     pages anonymous memory to 8 GB zram (zstd compressed) pool.
   - Level 3 Action: Sends D-Bus message to `kaatya-aid` to unload LLM weights to disk.
     If system pressure remains critical, `systemd-oomd` terminates low-priority cgroups.

3. USER NOTIFICATION & RECOVERY:
   - Displays notification: "Background tabs and idle AI unloaded to maintain responsiveness."
   - Workloads reload automatically when foreground user focus resumes.
