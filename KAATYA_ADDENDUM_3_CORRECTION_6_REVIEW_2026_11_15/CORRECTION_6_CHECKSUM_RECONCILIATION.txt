3. FORENSIC ROOT CAUSE ANALYSIS: THE SELF-REFERENTIAL HASH PARADOX
--------------------------------------------------------------------------------
Why did Value A appear in the internal table in Section 2?

Detailed inspection of the file generation workflow reveals the following:

1. Text Construction Phase:
   When `CORRECTION_5_FINAL_EVIDENCE_STATUS.txt` was drafted by the authoring script,
   Section 2 was designed to contain a markdown summary table listing the four core
   Correction 5 documents along with their sizes and SHA-256 checksums.
   The authoring script computed or estimated draft hashes for the documents.
   For the status document itself, a pre-computed hash string:
   `4d738ae69e514664c88204380c41a8e4ff7b198b0aeb3c77694feb5054d905f2` (Value A)
   was inserted into the table row.

2. The Self-Referential Paradox:
   SHA-256 is an avalanche-effect cryptographic hash function. Changing even a single bit
   in an input stream produces an entirely unpredictable 256-bit output.
   If a document embeds the string "4d738ae...", that 64-character string constitutes
   part of the byte stream being hashed.
   Unless an exact mathematical fixed point exists (where Hash(Document + Hash) == Hash)
   — which cannot be calculated practically under SHA-256 pre-image resistance —
   inserting ANY hash into a file will inevitably change the file's resulting hash.

3. Final Serialization Phase:
   When `CORRECTION_5_FINAL_EVIDENCE_STATUS.txt` was written to disk with Value A in its
   table, its actual resulting SHA-256 was computed by the filesystem and git as:
   `8ec4ef2c905e11aac64b6f3bb85d196d02c44d634e25dea96c7c66033b960c8e` (Value B).

4. Subsequent Manifest Generation:
   When the generator proceeded to Step 6 and created `CORRECTION_5_UPLOAD_MANIFEST.txt`,
   it performed a post-serialization disk read of all generated files. It measured the
   true hash of `CORRECTION_5_FINAL_EVIDENCE_STATUS.txt` (Value B) and recorded Value B
   in the upload manifest and in the inventory reconciliation report.
   However, the text *inside* `CORRECTION_5_FINAL_EVIDENCE_STATUS.txt` had already been
   written and still held the pre-generation draft string (Value A).
